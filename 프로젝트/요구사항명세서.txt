> **작성일**: 2026/005/18

---
  
  ## 1. 프로젝트 개요
  
  ### 1.1 프로젝트 목표
  > 이 앱이 해결하려는 문제와 만들고자 하는 가치를 1~2문장으로 정의한다.

이 프로젝트는 가계부 작성의 번거로움과 현금없는 사회에서의 지출 감각을 AI 기반의 영수증 자동 인식과 실시간 평균 시세 비교를 통해 해결한다. 
사용자가 번거로운 과정 없이 자신의 소비가 합리적인지 데이터로 판단하과, 지출에 대한 감각을 찾게 하는것이 이 앱의 핵심 가치이다.

### 1.2 대상 사용자
> 앱을 사용할 주요 사용자층

- 가계부를 작성하는 전업주부 , 대학생 , 자취생

### 1.3 핵심 가치
> 다른 비슷한 앱과 차별화되는 한 가지

- 기존 앱은 얼마를 썼는지 과거 기록만 보여준다면 이 앱은 도을 평균 시세 대비 합리적으로 잘 쓴 건지를 객관적으로 알려준다.

---
  
  ## 2. 기능 요구사항 (Functional Requirements)
  
  > 시스템이 *무엇을 하는가*를 정의한다. 최소 5개 이상 작성
> 문장 패턴: "사용자는 ~할 수 있다" / "시스템은 ~한다"

### FR-01: 영수증 및 결제 내역 이미지 촬영 및 업로드

- **설명**: 사용자는 기기의 카메라를 이용해 종이 영수증을 촬영하거나, 갤러리에서 토스 결제 내역 캡처본 이미지를 선택하여 시스템에 업로드할 수 있다.
- **수용 조건**:
  - [ ] 사용자가 촬영 버튼을 누르면 CameraX 라이브러리를 통해 카메라 화면이 정상적으로 구동되어야 한다.
- [ ] 사용자는 갤러리(미디어 보관함)에 접근하여 저장된 스크린샷 이미지를 선택할 수 있어야 한다.
- [ ] 시스템은 네트워크 부하를 줄이기 위해 업로드 전 이미지 파일을 적정 크기(예: 500KB 이하)로 자동 압축해야 한다.

### FR-02: LLM(Gemini) 기반 영수증 데이터 비정형 추출 및 파싱

- **설명**: 시스템은 업로드된 영수증 이미지의 텍스트를 인식하고, Gemini API를 통해 품목명, 금액, 날짜, 결제 수단, 구매처를 분류하여 구조화된 데이터로 변환한다.
- **수용 조건**:
  - [ ] 시스템은 이미지에서 추출한 텍스트 뭉치를 Gemini API의 멀티모달 기능으로 전달해야 한다.
- [ ] Gemini API로부터 가공하기 용이한 형태인 JSON 타입으로 응답을 받아야 한다.
- [ ] 응답 데이터에는 품목명, 단가/금액, 결제일시, 상호명 필드가 반드시 포함되어야 한다.

### FR-03: 공공데이터 API 연동 실시간 시세 비교

- **설명**: 시스템은 파싱된 품목명을 바탕으로 공공데이터포털의 생필품 가격 정보 API를 조회하여 해당 품목의 전국 평균 시세를 가져오고, 사용자의 구매가와 비교한다.
- **수용 조건**:
  - [ ] 시스템은 추출된 품목 키워드를 공공데이터 API의 검색 쿼리로 전송해야 한다.
- [ ] 시스템은 API로부터 반환된 당일 혹은 최신 평균 시세 데이터를 성공적으로 파싱해야 한다.
- [ ] 시스템은 '사용자 구매가 - 평균 시세' 를 계산하여 차액과 금액 비중(%)을 도출해야 한다.

### FR-04: 카카오/구글 맵 기반 소비 지도 시각화

- **설명**: 시스템은 영수증에서 추출된 상호명 정보를 기반으로 위치 좌표를 검색하고, 사용자가 돈을 지출한 위치를 지도에 마커로 표시한다. (추가 기능 여부 미확정)
- **수용 조건**:
  - [ ] 시스템은 추출된 상호명을 지도 로컬 API에 검색하여 위도와 경도 좌표를 회득한다.
- [ ] 사용자가 지도 화면을 켰을 대 해다 ㅇ좌표에 마커가 정상적으로 렌더링되어야 한다.
- [ ] 마커를 클릭하면 해당 장소에서 지출한 일시와 총 금액 팝업이 나타나야 한다.

### FR-05: 지출 내역 수동 편집 및 DB 저장

- **설명**: 사용자는 AI가 자동 입력한 가계부 내용 중 오류가 있으면, 직접 수정하거나 새로운 지출을 수동으로 입력할 수 있으며, 시스템은 이를 앱 내부 DB에 저장한다.
- **수용 조건**:
  - [ ] 사용자는 항목 추가/수정 화면에서 품목명, 금액, 카테고리를 직접 타이핑하여 변경할 수 있다.
- [ ] 사용자가 저장 버튼을 누르면 Android Room 라이브러리를 통해 로컬 SQLite DB에 데이터가 즉시 반영된다
- [ ] 오프라인 상태에서도 기존에 저장도니 지출 내역 리스트를 조회할 수 있어야 한다.

### FR-06: 소비 패턴 시각화 및 통계 차트 출력

- **설명**: 시스템은 로컬 DB에 저장도니 당일 지출 데이터를 카테고리별로 분류하여 UI에 시각적인 차트로 제공한다.
- **수용 조건**:
  - [ ] 시스템은 이번 달의 지출 금액을 상단에 직관적으로 표시해야 한다.
- [ ] MPAAndroidChart등의 라이브러리를 활용하여 카테고리별 지출 비율을 나타내는 원형 차트를 화면에 렌더링 해야한다.
- [ ] 사용자가 특정 카테고리를 탭하면 해당 카테고리의 세부 지출 목록 화면으로 이동해야 한다.


### FR-07: Gemini 기반 월간 소비 진단 피드백 제공

- **설명**: 시스템은 사용자의 한 달간 지추 ㄹ요약 데이터를 기반으로 Gemini API를 호출해 자연어 형태의 맞춤형 소비 개선 리포트를 생성한다.
- **수용 조건**:
  - [ ] 시스템은 월말에 사용자의 카테고리별 지출 총액 및 평균 시세 대비 과소비 품목 데이터를 취합해야한다.
- [ ] 취합된 데이터를 프롬프트에 녹여 Gemini API에 전달하고, 챗봇 형태나 리포트 형태의 텍스트 답변을 받아와야 한다.
- [ ] 사용자는 마이페이지 혹은 리포트 탭에서 AI가 제공하는 조언 문장을 명확히 읽을 수 있어야 한다.

  ## 3. 비기능 요구사항 (Non-Functional Requirements)
  
  > *어떻게 동작하는가*를 정의한다. 직접 보이지 않지만 품질을 결정한다.

### 3.1 성능 (Performance)

- 카메라 구동 속도: 사용자가 '영수증 촬영' 탭으로 이동했을 때, CameraX 기반의 카메라 프리뷰 화면이 1.5초 이내에 렌더링되어야 한다.
- AI 분석 응답 시간: 촬영된 이미지를 Gemini API로 전송하고 결과를 반환받아 화면에 표시하기까지의 과정은 정상적인 네트워크 환경에서 최대 5초 이내에 완료되어야 하며,
대기 시간 동안 사용자가 이탈하지 않도록 직관적인 로딩 UI를 제공해야 한다.
- 데이터베이스 조회: 메인 화면 진입 시 Room DB에 저장된 당월 지출 내역 및 통계 데이터를 불러오는 작업은 500ms 이내에 처리되어 화면 지연이 없어야 한다.

### 3.2 보안 (Security)

- (API 키 은닉: Gemini API, 공공데이터 API, 구글 API 키는 하드코딩되지 않아야 하며,local.properties와 BuildConfig를 활용해 관리하고 GitHub 등 공개 저장소에 절대
   노출되면 안된다.
   - 데이터 통신 보안 : 외부 API와 데이터를 주고받는 모든 네트워크 통신은 반드시 보안 프로토콜인 HTTPS를 사용하여 암호화되어야 한다.
   
   ### 3.3 사용성 (Usability)
   
   - 촬영 가이드 제공: 영수증 인식률을 높이기 위해, 카메라 촬영 화면에 영수증을 맞출 수 있는 시각적인 가이드라인을 제공해야 한다.
   - 오류 복구 및 피드백: 구겨진 영수증 등으로 인해 AI OCR 인식이 실패하거나 네트워크 오류가 발생할 경우,
   앱이 강제 종료되지 않고 사용자에 에러 메시지와 함께 '수동 입력 화면'으로 자연스럽게 유도해야 한다.
   - 접근성 준수: 앱 내의 모든 주요 터치 영역(버튼, 입력 폼 등)은 안드로이드 접근성 가이드라인에 따라 최소 48x48dp 이상의 크기를 가져야 한다.
   
   ### 3.4 호환성 (Compatibility)
   
   - OS 버전 지원: 이 앱은 Android 8.0 이상을 타겟으로 하여 개발되며, 현재 사용되는 안드로이드 기기의 90% 이상에서 정상 동작해야 한다.
   - 화면 대응 : 스마트폰의 세로 모드를 기본으로 최적화한다.
   
   ### 3.5 기타
   
   - 확장성 : 외부 API 통신 모듈은 느슨하게 결합되도록 설계하여 추후 Gemini API 대신 다른 LLM으로 변경하거나 공공데이터 API 주소가 바뀌더라도 코어 로직 수정이 최소화 되도록 구성되어야 한다.
